# 1c-client: тонкий клиент 1С на отдельной машине

Сервер (папка 1c-server) работает на другой машине. Клиент находит его по IP-адресу.

## Подготовка

1. На машине сервера: `./start.sh`, затем откройте порты файрвола 1540-1541/tcp
   и 1560-1591/tcp (для firewalld: `sudo firewall-cmd --permanent --add-port=1540-1541/tcp
   --add-port=1560-1591/tcp && sudo firewall-cmd --reload`).
2. На клиентской машине положите в dist/ установщик `setup-full-<версия>-x86_64.run`
   (или .deb тонкого клиента, см. dist/README.txt).
3. В .env впишите SERVER_IP (IP машины с сервером) и ту же ONEC_VERSION, что у сервера.

## Работа

```bash
chmod +x *.sh
./build.sh             # сборка образа (.deb или .run)
./client.sh check      # проверка доступности сервера (1540/1541; 1560/1561 — информационно)
./license.sh activate  # получить лицензию в окне 1С
./license.sh install   # собрать .lic в ./licenses
./license.sh push user@СЕРВЕР:/путь/к/1c-server/licenses/
./client.sh            # запуск 1С (всегда один и тот же контейнер)
./client.sh shell      # консоль в контейнере (графика не нужна)
./reset.sh             # удалить контейнер и его данные
```

В окне 1С база добавляется как "На сервере 1С:Предприятия": кластер onec-server:1541, имя mybase.
Имя onec-server клиентский контейнер направляет на SERVER_IP (extra_hosts в docker-compose.yml);
оно нужно, потому что кластер сообщает клиенту именно это имя.

Если поменяли SERVER_IP: `./client.sh recreate`.

## Архитектура: amd64 и arm64

В dist/ можно держать пакеты разных архитектур и версий: при сборке выбираются только те,
что подходят архитектуре машины (amd64 или arm64) и версии ONEC_VERSION из .env,
остальные пропускаются (в логе будет «Пропускаю ...»). Если подходящих нет, сборка
остановится с понятным сообщением. Платформа ставится в /opt/1cv8/current.
Клиент и сервер могут быть на машинах разной архитектуры, но версия платформы должна совпадать.

## Установщик .run

Если для версии нет .deb, положите в dist/ установщик
`setup-full-<версия>-x86_64.run` или `setup-thin-<версия>-x86_64.run`. Он ставится без графики
командой `--mode unattended --enable-components client_full,client_thin,ru`. Список компонентов
меняется переменной ONEC_RUN_COMPONENTS в .env (имена компонентов см. в `./установщик.run --help`).
Версия в имени файла должна совпадать с ONEC_VERSION.

Примечание: установщик `setup-thin-*.run` ставит тонкий клиент сам (в нём --enable-components
принимает только языки), поэтому для него компоненты не передаются. Для `setup-full-*.run`
используется ONEC_RUN_COMPONENTS (по умолчанию `client_full,client_thin,ru`).

## Сетевой ключ HASP (NetHASP)

Адреса менеджеров лицензий задаются в .env (NETHASP_ADDRS); из них скрипты собирают
nethasp.ini, который **монтируется** в контейнер в /opt/1cv8/conf/nethasp.ini.
Пересобирать образ после смены адресов не нужно — достаточно `./client.sh recreate`.
Имена хостов в NH_SERVER_ADDR (например MEGABYTEPLUS) должны резолвиться из контейнера;
если нет, замените их на IP. Менеджер лицензий слушает порт 475 (UDP и TCP).
В клиент-серверном режиме такой же файл нужен серверу (1c-server/server/nethasp.ini).

## Выгрузка базы на компьютер (.dt)

```bash
./export-db.sh mybase [пользователь] [пароль]
```

Файл появится в `./export/backup/dt` (для `.dt`) или `./export/backup/cf` (для `.cf`). Нужен полный клиент: положите в dist/ setup-full-<версия>-x86_64.run
(тонкий установщик setup-thin конфигуратор не содержит), пересоберите образ и пересоздайте контейнер.
Перед выгрузкой завершите сеансы пользователей в базе.

## Дамп с сервера на этот компьютер

Два способа, оба кладут файл в ./export:

1. `./export-db.sh mybase [пользователь]`: конфигуратор клиентского контейнера подключается к серверу
   по сети и выгружает .dt (нужен полный клиент в образе клиента).
2. `./pull-backup.sh [--move] [база] [пользователь]`: дамп делает сам сервер (`./backup.sh`), а файл
   копируется на этот компьютер по SSH. `--pg` забирает дамп PostgreSQL (.dump).
   В .env задайте SERVER_SSH, SERVER_PROJECT_DIR (абсолютный путь к 1c-server на сервере)
   и при необходимости SERVER_SSH_OPTS. Удобнее настроить вход по ключу: `ssh-copy-id user@сервер`.

Имя базы по умолчанию берётся из IB_NAME в .env.

## Куда попадают выгрузки

Все выгрузки сохраняются на этом компьютере в каталог EXPORT_DIR из .env (по умолчанию ./export,
можно указать любой, например /home/student/1c-dumps) и остаются там при удалении контейнеров.
Файлы `.dt` хранятся в `EXPORT_DIR/backup/dt`, `.cf` — в `EXPORT_DIR/backup/cf`; дампы PostgreSQL при получении через `pull-backup.sh --pg` — в `EXPORT_DIR/backup/pg`.
Способы получить файл:

    ./export-db.sh mybase [пользователь]   # выгрузка конфигуратором по сети
    ./export-db.sh --pull                  # забрать самый свежий .dt, сделанный на сервере (scp)
    ./export-db.sh --remote mybase [польз] # запустить ./backup.sh на сервере по ssh и забрать файл

Для --pull и --remote задайте SERVER_BACKUP_SRC=пользователь@сервер:/путь/к/1c-server/backups.

## Пользователь в контейнере

Контейнер работает от пользователя с UID из CLIENT_UID (.env, по умолчанию 1000) — это нужно
для доступа к X11 и чтобы файлы в ./export принадлежали вам. Узнать свой UID: `id -u`.
После смены CLIENT_UID выполните `./reset.sh` (пропадут только список баз и настройки клиента).

## Установка платформы (install-platform.sh)

Dockerfile вызывает install-platform.sh: он берёт из dist/ .deb или .run своей архитектуры и версии
ONEC_VERSION, подбирает допустимые компоненты для setup-full*.run по справке установщика, а после
установки проверяет наличие нужных бинарников (1cv8c). При ошибке в логе сборки будут справка установщика
и содержимое каталога платформы.
